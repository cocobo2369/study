
# 1.3 선언, 정의, 링키지
- 선언
- 정의 : 선언의 구현, 메모리 할당
- 링키지 : 서로다른 스코프의 어떤 이름이 어떤 개체를 지칭하는지 알아내기위한 탐색

# 1.3.1 선언 vs 정의
- header 에 선언하지 않고 cpp에만 함수 선언 및 정의
  - 자유 함수를 그 스코프 안에서 정의(나쁜 아이디어)
  - 선언과 정의 간 시그니처의 불일치는 컴파일 타임에 발견되지 않는다.

# 1.5 include 지시자와 include 가드
- 권장
```cpp
#include <xxx>
```
## 1.5.1 인클루드 지시자
- 별 생각 없이 썼지만 `#include "xxx"` 와 `#include <xxx>` 가 차이를 잘 알지 못했다.

- `""` 은 호출하는 cpp와 동일폴더를 찾음.
  - 이름이 동일한 경우 충돌을 피함
  - 게으른 방식

- `<>` 은 현재 소스 경로에서 찾는 것을 생략하고 다른 경로를 먼저 찾음.
  - 개발도구와 빌드 도구에 로컬 헤더 경로의 통제권을 줄  수 있고 정확하게 헤더를 찾음
  - 개발 및 배포에 유연성을 줌

- #include 전처리 지시자를 쓰면 헤더파일의 내용이 단순 텍스트 지시자가 있는 라인과 치환된다.

## 1.5.2 내부 인클루드 가드
```cpp
//my_func.h

#ifndef INCLUDED_MY_FUNC
#define INCLUDED_MY_FUNC

// ... - #include 지시자

namesapce my{ //--my는 고유한 네임스페이스

// ... 헤더파일 몸체

}

#endif
```

# 1.6 단순한 .h/.cpp 쌍에서 컴포넌트로
## 1.6.1 컴포넌트 속성 1
- cpp 파일이 구현하고자 하는 헤더파일이 항상 맨 앞에 위치해야한다!
  - 그래야 모든 헤더 파일이 독립적으로 컴파일되게 하고 `인클루드 순서`에 따른 문제를 원천적으로 예방

## 1.6.2 컴포넌트 속성 2
- .cpp 파일에 정의된 외부 링키지를 갖는 논리적 구문은 대응되는 .h 파일에 그 선언이 있어야한다. 그렇지 않은 경우 외부에 노출되는 효과가 없도록 처리해야 한다.
  - 외부에서 접근해야하는 정의는 모두 .h 파일에 선언해야한다.cpp에 구현의 선언은 h에 있어야한다! 는 뜻인듯

## 1.6.3 컴포넌트 속성 3
- 외부 또는 듀얼 바인디지를 갖는 논리적 구문이 컴포넌트의 헤더 파일에 선언되었다면 그 컴포넌트 안에 정의부가 존재해야 한다. 그렇지 않은 경우 정의 자체가 없어야 한다.

## 1.6.4 정리
1. 헤더는 반드시 코드의 제일 앞에서 인클루드 되어야 한다.
2. 각각의 외부 링키지 정의는 반드시 헤더에 선언해야 한다.
3. 헤더에 선언된 각각의 외부 또는 바인디지 개체는 그 정의가 같은 컴포넌트 안에 존재해야한다.
